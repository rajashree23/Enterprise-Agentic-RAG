# Execution Plan Contract

## 1. Purpose

The planning LLM receives identified sub-queries and registered capability
descriptions, including supported arguments.

It selects operations and dependencies. The application validates the
plan, generates step IDs, and passes the resulting plan to the executor.

### Current Milestone Constraint

The GitHub-only milestone requires exactly one retrieval step for every
decomposed sub-query. The planner does not yet represent clarification,
unsupported, context-sufficient, or multiple-steps-per-sub-query outcomes.
This is a temporary milestone constraint rather than the target orchestration
model.

## 2. Schema

| Field | Type | Ownership | Meaning and consumer |
|---|---|---|---|
| `execution_steps` | array of objects | LLM-generated | Planned operations, validated by the application and used by the executor. |
| `sub_query_id` | string | Application-generated; referenced by LLM | Existing sub-query addressed by the step. Used for validation and traceability. |
| `action` | string | LLM-generated | Description of the intended operation. Not automatically passed to the tool. |
| `capability` | string | Application-defined; selected by LLM | Registered capability identifier used by the executor to select a tool. |
| `arguments` | object | LLM-generated | Capability-specific parameters validated by the application and passed to the tool. |
| `depends_on_sub_query_ids` | array of strings | Existing application IDs selected by LLM | Dependencies in the LLM output. The application translates them into step references. |
| `step_id` | string | Application-generated | Identifies an execution step. Used by execution, results, and evidence. Not generated by the LLM. |
| `depends_on` | array of strings | Application-derived | Step IDs that must complete successfully before this step runs. Used by the executor. |

The LLM output requires all fields shown in its example.
The application output replaces `depends_on_sub_query_ids` with
`depends_on` and adds `step_id`.

In the application model, `arguments` defaults to an empty object if
omitted. Other application-plan fields are required.

IDs must be treated as opaque strings.

## 3. Rules

- Each input sub-query must appear exactly once in the plan.
- Capabilities and sub-query references must exist.
- Dependencies cannot contain unknown IDs, duplicates, self-references,
  or cycles.
- An empty dependency list means the step can run independently.
- Unexpected fields in LLM output are rejected.
- Tool arguments are validated at execution, not merely by plan parsing.
- Dependencies control scheduling; they do not automatically pass one
  step's output into another step's arguments.
- The executor invokes tools using application code, not another LLM call.

## 4. LLM Output Example

```json
{
  "execution_steps": [
    {
      "sub_query_id": "sq-1",
      "action": "Retrieve issue details",
      "capability": "github.get_issue",
      "arguments": {
        "owner": "rajashree23",
        "repo": "agentic-rag-demo-data",
        "issue_number": 1
      },
      "depends_on_sub_query_ids": []
    }
  ]
}
```

## 5. Application Output Example

```json
{
  "execution_steps": [
    {
      "step_id": "step-1",
      "sub_query_id": "sq-1",
      "action": "Retrieve issue details",
      "capability": "github.get_issue",
      "arguments": {
        "owner": "rajashree23",
        "repo": "agentic-rag-demo-data",
        "issue_number": 1
      },
      "depends_on": []
    }
  ]
}
```
